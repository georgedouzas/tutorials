**Facts the design relies on:**

- **The template already asks for ten and ten.** `openspec/templates/chapter.qmd` asks for ten examples and ten
  exercises per statement, but the `tutorial-content` spec still says three.
  - The archived change `2026-11-19-physics-tutorials-ten-examples` raised the minimum for Theoretical Physics.
  - It was archived with 2 of 18 tasks done and its delta was not synced.
  - This change follows its approach (a list of raised chapters, one task per chapter), but for this tutorial only.
- **No checker remains.** The check scripts (`density.py`, `check_format.py`) were removed with Sage and Lean in
  commit `99a3d9a`. Only `_filters/harvest.py`, the cross-reference index, remains.
- **No figure can be regenerated.** The figure scripts were removed in the same commit.
  - Captions still name them ("Generated by `figures/<name>.sage`").
  - The figures are 101 SVG and 14 PNG files, plus 13 interactive Plotly or threejs pages under
    `figures/interactive/`, embedded by `_filters/interactive.lua`.
- **How Sage appears today.** Sage code is shown as a fenced `python` block, followed by `*Output:*` and a `text`
  block. The output was pasted in, and nothing re-runs it.
- **Tools.** SageMath 10.9 is at `/usr/local/bin/sage`.
- **Where the gaps are recorded.** The coverage record is
  `openspec/changes/archive/2026-11-18-tutorials-missing-chapters/coverage/fundamentals-of-mathematics-for-physicists.md`.
- **No Verification boxes.** This tutorial has no Verification callouts, so the `result-verification` spec is not
  touched.

## Goals / Non-Goals

**Goals:**
- Exactly ten examples and ten exercises per statement in every chapter of Fundamentals of Mathematics for
  Physicists.
- Every exercise solution with a Proof tab and a SageMath tab.
- Every figure of the tutorial audited, regenerated by a committed Sage script, and given a simple caption.
- The 20 recorded gaps filled, and the two planned chapters written.
- A content checker that keeps all of this true, so that the work can stop after any chapter with the build green.

**Non-Goals:**
- Raising the other tutorials to ten and ten, or regenerating their figures. Only their captions are simplified.
- Lean or Veriphy verification.
- Changing the order of the chapters or the topics of existing statements, except to fix errors found on the way.

## Decisions

### M1. Exactly ten and ten

Every `def-`, `thm-`, `lem-`, `prp-` and `cor-` block is followed by exactly ten `exm-` blocks in its Examples fold
and exactly ten `exr-` blocks in its Exercises fold (the owner's rule: ten, not more). Existing blocks count towards
the ten; when there are more good candidates than places, the weakest is dropped.

**Grading.**
- **Examples:** the simplest instances first, then the standard cases, then cases from physics, then limits and
  counterexamples. Physics cases come from the tutorial's running systems: `S^1`, `S^2`, `SU(2)`, the harmonic
  oscillator, the hydrogen atom, Minkowski space.
- **Exercises:** direct checks first, then computations, then proofs, then problems that combine the statement with
  earlier ones.

**Exceptions.** A statement such as a technical lemma may not support ten good items. It gets as many as the material
supports, between three and ten, and is listed in `_raised.txt` as `<chapter> <label> <reason>`.

### M2. Raised chapters

`fundamentals-of-mathematics-for-physicists/_raised.txt` lists one chapter slug per line, plus the exception lines of
M1. The content checker applies the new rules only to listed chapters:

- ten and ten;
- both solution tabs;
- the caption rule, the figure scripts and the re-run Sage outputs.

Other chapters keep the minimum of three. A chapter is added to the list by the task that raises it, in the same
commit, so the build stays green whenever the work stops.

### M3. Solution tabs

Each solution keeps its collapsed `.solution` callout. Inside the callout is a Quarto tabset with the Proof tab first:

````markdown
::: {.callout-note .solution collapse="true" title="Solution"}
:::: {.panel-tabset .solution-tabs}
## Proof

<theoretical solution>

## SageMath

<one sentence: what the code computes or, for a proof exercise, which concrete case it checks>

```{.python .sage}
<code>
```

```{.text .sage-output}
<recorded output>
```
::::
:::
````

- **Labels:** the tab headings are exactly "Proof" and "SageMath", written that way (no capitals, no monospace).
- **Colours:** the two tabs and their panes have the same style and colour (the owner's review). What sets the
  SageMath tab apart is its content: the code block and the output block, each with a small teal label.
- **Code fences:** the code fence is `{.python .sage}`, so Quarto highlights it as Python and the class `sage` marks it.
  The output is a `text` block with the class `sage-output`, which replaces the old `*Output:*` line.
- **Labels on the blocks:** the code and the output carry small teal "sage" and "output" labels.
- **PDF:** tabsets render one after the other with their headings, so the PDF shows both forms in order.
- **Proof exercises:** the SageMath tab opens with "Check on <instance>:", names the instance, and ends its code with
  a `print` of a boolean or of the compared values. It never claims to prove the statement.
- **Integrative exercises:** the closing `## Exercises` section of each chapter follows the same form.

*Alternative considered:* two separate folds, one per form. Rejected: twice as many folds per exercise, and the owner
chose tabs.

### M4. Sage code is re-run by the content checker

`_filters/check_content.py <tutorial> [<chapter> ...]` lives next to `harvest.py`. For each raised chapter it does
the following:

1. **Counts.** It parses the chapter with the same block patterns as the count above. It reports each statement
   whose examples or exercises are not exactly ten, unless the statement is a listed exception (three to ten).
2. **Solutions.** It checks that every `.solution` has a `panel-tabset` with a Proof tab and a SageMath tab, in that
   order. The SageMath tab must contain one `sage` block followed by one `sage-output` block.
3. **Sage outputs.** It runs every SageMath tab and every Sage example (`exm-` blocks with a `sage` block) in one Sage
   process per chapter, each block in a fresh namespace. It compares each block's standard output with the recorded
   output after removing trailing spaces. With `--update` it writes the new output into the page instead; the author
   reviews the diff.
4. **Figures.**
   - Every image the chapter references must have a `figures/<name>.sage` that writes it.
   - With `--figures`, the scripts are run and the files they write are compared with the files the chapter
     references.
   - Captions are checked against the rule of M6.

The checker exits non-zero on any finding. It is run by each chapter task, never by the site render: the render does
not need Sage, because the outputs are recorded in the pages.

*Alternative considered:* Quarto's own code execution with a Sage kernel. Rejected: it would make every render depend
on Sage and on a Jupyter kernel, and the freeze cache would double the repo size.

### M5. Figure scripts next to their figures

Each figure has `figures/<name>.sage` in its chapter folder.

- **Running.** The script runs from the chapter folder with `sage figures/<name>.sage`. It writes
  `figures/<name>.svg`, a PNG only for raster content such as domain colouring, and, where M7 applies,
  `figures/interactive/<name>.html`.
- **Rendering.** `.sage` files are ignored by the site render because they are not `.qmd`, and they are not linked
  from any page.
- **Shared style.** Scripts share one style module, `_filters/figstyle.sage`, loaded with `load()`. It holds the
  palette (the site's accent and block colours), the font sizes, transparent backgrounds, and line colours that read
  in both themes.
- **Notation.** Labels use the symbols of `_notation/`.
- **Existing figures.** All 115 are recreated as scripts. The existing image is the reference for what to draw, and
  the audit of M7 decides whether it is kept, corrected or replaced.

### M6. Simple captions, site-wide

A caption is at most two sentences:

- It says what the figure shows and the parameters needed to read it, for example "Lower and upper Riemann sums of
  x² on [0, 1] with 4 and 16 subintervals."
- It has no "Generated by", no file names, and does not mention SageMath or Plotly.
- Explanations that belong to the text move into the prose before the figure.

The content checker flags captions that break the rule in every tutorial. The captions of Theoretical Physics (about
220) and Kaluza-Klein Theories (about 50) are fixed in one text-only task. Their figures are not regenerated.

### M7. The figure audit

The audit is done for each chapter as part of its task. Each figure is checked against four questions, and the
outcome is recorded in the task's report:

1. Does it show what the text and the caption say? The values are recomputed by its script.
2. Does it use the site notation?
3. Is it legible in light and dark mode at the width it is shown? This is checked with a headless screenshot of the
   rendered page in both modes.
4. Does the text use it? If not, the text gains a sentence that uses it, or the figure is removed.

**Missing figures.** Each drawable statement without a figure gets one in one of its examples. Drawable means a set in
the plane, a curve, a surface, a vector field, a flow, a spectrum, a distribution, a group orbit or a coset picture.

**Interactive versions.** Surfaces, vector fields, orbits and potentials also get an interactive version: threejs
for 3D, Plotly for 2D, as today.

### M8. Sources

**Where the material comes from.**
- New statements, examples and exercises come first from the textbooks that the Zotero reading notes (child notes
  tagged `tutorial-reading-note`) map to the chapter.
- They are rewritten in the site notation and the tutorial's voice, never copied.
- An adapted item cites `[@key, Example n]` or `[@key, Problem n]`, and every key exists in
  `references/references.bib`.

**Problem books in the library.**

| Chapter | Problem books |
|---|---|
| Sets, relations and topology | `cheung2024metric` |
| Real analysis | `gasinski2014exercises` |
| All chapters | `aliev2024mathematical` |

The textbook exercises of `axler2024linear`, `lee2013introduction`, `keskivakkuri2022mathematical`,
`mukunda2022continuous` and `rudolph2013differential` are also used. Before each chapter, the task searches the Zotero
library semantically for further problem collections on the chapter's subject.

**A source the library lacks.** The task names the needed book and stops for the owner. Nothing is added to Zotero
without the owner's approval.

**Reading notes.** Each task drafts the additions to the reading notes, the sections and problems it used, in
`reading-notes/<chapter>.md` of this change. They are written to Zotero in one batch when the change closes (task
5.1), after the owner approves the whole set. Until then the drafts in the repo are the record.

**PDF text.** Textbook PDFs are read with `zotero_read_pdf_pages`, or from the Mathpix OCR where the PDF is scanned.

### M9. Gaps and planned chapters

**Where the coverage record lives.** The record is copied out of the archive to
`openspec/coverage/fundamentals-of-mathematics-for-physicists.md`. This is now its live location; the copy in the
archive stays as history. Each filled gap is marked `done (sec-<id>)` there.

**Gaps.** Each gap becomes a `##` section, or a `###` unit when it is small, in the chapter the record names, at the
point the bottom-up order allows. It is written during that chapter's task.

**Planned chapters.** Calculus of variations and Homotopy and cohomology are written from `openspec/templates/chapter.qmd`
with the scope given in the record. Each is its own task, at its place in reading order. When a chapter is written,
its `_quarto.yml` entry loses the planned badge and goes back to a plain path, and the landing page's line for it is
updated.

**Gaps found later.** A further gap found while raising a chapter is added if later chapters or tutorials use the
topic. Otherwise it is recorded in the coverage record with the reason it is left out.

### M10. Order and the pilot

**Pilot.**
- Linear algebra is the pilot. It is small (26 statements), it has two recorded gaps, it already mixes theory-only and
  Sage solutions, and it has 4 figures.
- After the pilot the work stops for the owner's review of the layout, the tabs, the captions, the density and the
  sources. Changes the review asks for are folded into this design and the template before any other chapter starts.

**The remaining chapters.**
- They follow in reading order, with the two planned chapters at their places.
- Each chapter is one task and one commit. The task fills the chapter's gaps, adds ten and ten, converts its
  solutions to tabs, regenerates and audits its figures, lists the chapter in `_raised.txt`, and runs the checker,
  `harvest.py` and the render.
- Chapters that need more than about 400 new blocks are done one `##` section per agent run: Hilbert spaces,
  Differential geometry, Lie groups and Spinors.

**The template.** `openspec/templates/chapter.qmd` gains the solution-tab form of M3 and the caption rule, so that new
chapters in every tutorial start from it.

### M11. Decisions from the pilot review

**Bold vectors and matrices.** The notation page wins: a column vector of $\mathbb R^n$ or $\mathbb C^n$ is bold
($\mathbf v$), a matrix is bold uppercase ($\mathbf A$, $\mathbf I$), and an abstract vector, a linear map and an
element of a space with no chosen basis stay plain ($v \in V$, $T: V \to W$). A linear map and its matrix in a basis
are told apart this way. Named matrices of physics keep their own symbols: $\eta$, $\Lambda$, $\sigma_a$,
$\gamma^\mu$, $g$, $\rho$, $\boldsymbol\Sigma$. Each chapter is converted when it is raised.

**Forward references.** A statement or a proof never uses a later result as a step. A remark, an example or an
exercise may link forward to a later section for a familiar fact (a $2 \times 2$ determinant, a trace), saying that
the fact is proved there. The determinant stays after multilinear maps, because it is built from alternating forms;
the earlier sections link forward to it.

**Overlaps between chapters.** When a proof needs a special case of a theorem proved in a later chapter, the special
case is proved where it is needed, and a remark names the later theorem. The proof of the singular value decomposition
keeps its orthonormal eigenbasis for real symmetric matrices and points to @thm-spectral-theorem-hermitian.

**New symbols.** New symbols go into the shared notation tables (`_notation/`) as each chapter is raised. A symbol used
only inside one proof, such as $\omega_e$ in the construction of the determinant, stays local.

## Risks / Trade-offs

- **Cost.**
  - **Risk:** about 9,000 new blocks, in the order of 55M agent tokens.
  - **Mitigation:** one task per chapter in a fixed order, with the pilot review first, so the owner can stop after
    any chapter.
- **Repetitive items.**
  - **Risk:** ten variations of the same computation.
  - **Mitigation:** the grading of M1 and the problem books give variety. Each task's report names the sources it
    used, so a thin chapter shows.
- **A SageMath tab that adds nothing to a proof.**
  - **Risk:** a check that only restates the claim.
  - **Mitigation:** the check must name a concrete instance and compute something about it, a matrix, a group or a
    function, that the reader could not see at a glance.
- **Sage output drift.**
  - **Risk:** a later Sage version prints differently.
  - **Mitigation:** `check_content.py --update` rewrites the outputs, and the author reviews the diff. The site never
    runs Sage.
- **Length.**
  - **Risk:** chapters roughly triple.
  - **Mitigation:** the Examples and Exercises folds stay collapsed, so the line of argument does not grow. The search
    index (`search.json`, already 24 MB) will grow too. If the upload starts failing, a follow-up can exclude the
    folds from the index.
- **Cross-references.**
  - **Risk:** new sections in existing chapters shift content.
  - **Mitigation:** identifiers are number-free slugs and never change. Each task runs `harvest.py` and the render
    and checks that no reference is unresolved.
- **Approved-only Zotero writes.**
  - **Risk:** the tasks stop to ask.
  - **Mitigation:** the reading-note additions wait in the repo and go to Zotero in one approved batch at the close
    (M8).
